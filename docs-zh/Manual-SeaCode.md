# SeaCode - 使用手册

## 版本信息

| 项目 | 内容 |
| --- | --- |
| 运行方式 | 本地 Python 应用 |
| Python | 3.12 或更高版本 |
| 包管理 | `uv` |
| 主入口 | `sea` |
| 配置位置 | 项目配置与用户配置 |

## 1. 环境准备

需要准备：

- Python 3.12+
- `uv`
- Git
- 一个可用的模型 Provider 和对应凭据
- 支持 UTF-8 的终端

在 Windows、macOS 或 Linux 上使用时，应确保 `python`、`uv` 和 `git` 都能从终端直接调用。

## 2. 安装与启动

在项目目录执行：

```bash
uv sync
uv run sea --help
uv run sea
```

安装为本地命令后，也可以直接使用：

```bash
sea
```

启动后，界面会显示当前工作目录、活动模型、会话状态和输入区域。首次运行建议先执行 `/status` 检查配置与工具状态。

## 3. 配置模型 Provider

推荐把密钥放在本地环境文件或系统环境中，不要提交到 Git。配置名遵循外部 Provider 的协议契约，SeaCode 自己的运行参数使用 `SEA_` 前缀。

示例：

```dotenv
ANTHROPIC_API_KEY=replace-with-your-key
ANTHROPIC_BASE_URL=https://api.example.com/anthropic
SEA_LLM_DEFAULT_MODEL=replace-with-your-model
SEA_MAX_STEPS=100
```

注意：

- 示例值不是可用凭据。
- 不要把真实密钥写进日志、截图、测试 fixture 或会话内容。
- `ANTHROPIC_BASE_URL` 只在 Provider 需要自定义端点时设置。
- 模型名称应与端点实际支持的模型一致。

## 4. 第一次任务

建议从可验证、影响范围小的任务开始：

```text
请先检查当前项目的测试入口，说明你准备查看哪些文件，不要修改文件。
```

确认计划后，再提交一个明确的变更任务：

```text
请修复指定测试失败。先读取相关实现和测试，修改前说明原因，修改后运行最小相关测试并报告结果。
```

对于需要写文件或执行命令的操作，SeaCode 会按照当前权限模式处理。让任务包含“先读、再改、再验证”，通常更容易得到可复核的结果。

## 5. 常用命令

| 命令 | 作用 |
| --- | --- |
| `/help` | 列出可用命令。 |
| `/status` | 查看模型、权限、工具、目录和用量状态。 |
| `/plan` | 进入只读规划模式。 |
| `/do` | 根据当前计划进入执行流程。 |
| `/compact` | 手动压缩较早的对话上下文。 |
| `/resume` | 从历史会话中选择并恢复。 |
| `/clear` | 结束当前会话并创建新会话。 |
| `/session` | 查看当前会话标识和存档信息。 |
| `/permission` | 查看当前权限模式。 |
| `/exit` | 安全退出。 |

输入 `/` 后可以使用候选菜单；多行任务可在输入框中编辑后提交。

## 6. 权限模式

| 模式 | 适合场景 |
| --- | --- |
| `default` | 日常开发，读操作自动放行，写入和命令需要确认。 |
| `acceptEdits` | 信任文件修改，希望仍确认命令执行。 |
| `plan` | 只探索代码和生成计划，不执行修改。 |
| `bypassPermissions` | 受控环境中的快速自动化，使用前确认工作区和命令风险。 |

无论模式如何，危险命令保护和路径边界都应优先生效。需要确认时，选择“本次允许”只影响当前调用；选择“持续允许”会写入当前工作区的规则；拒绝不会关闭会话。

## 7. 会话与运行记录

SeaCode 会把会话、工具结果和运行元数据保存在用户运行目录中。运行记录用于恢复、排障和上下文治理，不应作为源代码提交。

建议：

- 使用 `/session` 确认当前会话标识。
- 长任务定期查看 `/status` 的用量与迭代状态。
- 任务完成后保留必要的测试输出和最终变更说明。
- 不要把包含凭据的运行记录上传到公共位置。

## 8. Git 工作区与并行任务

需要隔离变更时，先让 Agent 创建一个有意义的工作区名称，再在其中执行任务。退出或清理前，SeaCode 会检查未提交修改和新增提交；发现变更时默认保留工作区，避免误删成果。

子 Agent 或团队任务完成后，先检查其工作区、测试结果和待合并变更，再决定是否清理。自动化并不替代代码评审。

## 9. 常见问题

### 启动时提示找不到密钥

检查环境变量名称、环境文件位置和当前终端是否重新加载了配置。不要把密钥直接粘贴到对话框中。

### 模型返回鉴权或模型不存在

检查端点地址、模型名称和 Provider 协议是否匹配。可以先用 `/status` 确认当前活动配置，再重新发起一条短消息。

### 工具调用被拒绝

查看界面中的拒绝原因：可能是权限模式、规则、路径边界或危险操作保护。调整任务范围或显式确认，不要通过模糊命令绕过保护。

### 上下文变得很长

使用 `/compact`，或者让 Agent 先总结当前目标、已完成工作、失败原因和下一步。压缩会保留近期原文和可重读的工具结果。

### 工作区无法删除

通常表示其中有未提交修改或新增提交。进入工作区检查差异，确认结果已经保存后再使用带丢弃选项的清理操作。

### TUI 显示异常

确认终端支持 UTF-8，窗口宽度足够，并重新启动 `sea`。如果问题只在某个 Provider 请求期间出现，先查看错误事件和网络配置。

## 10. 安全检查清单

- [ ] 密钥只存在于本地安全配置中。
- [ ] 当前工作目录是预期的项目目录。
- [ ] 重要写入前使用 `default` 或 `plan` 模式确认范围。
- [ ] 未提交变更已通过测试或已明确记录。
- [ ] 分享日志、截图和会话前已移除敏感信息。
